# Инструкции для AI-агентов

Этот файл нужно читать в начале новой сессии работы с проектом, после потери/сжатия контекста или если есть сомнение, что правила в памяти актуальны.
Если агент меняется или контекст был потерян, сначала прочитай:

1. `AGENTS.md` — постоянные правила работы.
2. `AI_CURRENT_CONTEXT.md` — текущий рабочий контекст и незавершенные решения.
3. `AI_WORK_PLAN.md` — активная задача и ближайшие шаги.
4. `AI_PROJECT_MAP.md` — только нужные разделы карты архитектуры проекта.

Если эти файлы уже прочитаны в текущем сохраненном контексте, не перечитывай их полностью на каждый пользовательский запрос: используй уже загруженную память, а к файлам обращайся точечно только при смене задачи, сомнении, конфликте правил или после их изменения.

## Рабочий процесс

- При старте всегда проверяй `AI_WORK_PLAN.md` - вдруг уже выполняется какая - либо задача и работа предыдущего ассистента была внезапно прервана. Нужно в таком случае её продолжить.
- Не считай абсолютные пути из контекстных файлов переносимыми. На новой машине заново определи корень проекта по `.git`, `AGENTS.md`, `AI_CURRENT_CONTEXT.md` и `AI_PROJECT_MAP.md`.
- Перед изменениями проверяй `git status --short --branch`.
- Перед реализацией новой функциональности сначала проверь реализуемость: какие права, сервисы, контейнеры, CLI-инструменты, внешние API, фоновые процессы и доступы нужны. Если задача требует недоступных или опасных возможностей (например Docker socket из WebAdmin, root-доступ, запись в production-файлы, управление git/deploy из HTTP), явно назови ограничение и риск до начала работ и предложи более простой/безопасный вариант. Не строй крупный функционал на неподтвержденных предположениях об окружении.
- Перед началом работы над задачей создавай или обновляй `AI_WORK_PLAN.md`: краткая цель, чеклист со статусами `[pending]`, `[in_progress]`, `[completed]`, важные заметки и блокеры. В ходе выполнения отмечай прогресс в этом файле, чтобы после зависания машины или смены ассистента можно было продолжить без повторного расследования.
- При продолжении работы после паузы или смены ассистента перечитывай `AI_WORK_PLAN.md` — пользователь мог добавить задачи или изменить приоритеты, пока ассистент не работал.
- Держи `AI_WORK_PLAN.md` коротким: активная задача, недавние 1-3 задачи и ссылки на архивы. Старые подробные планы переноси в `archive/`, а не копируй в основной рабочий файл.
- Если есть чужие изменения, не трогай их, если они не мешают текущей задаче.
- Делай минимальные правки в рамках запроса.
- После существенных действий обновляй `AI_CURRENT_CONTEXT.md`: что сделано, какие файлы тронуты, какие проверки выполнены, что осталось. Держи файл как короткий рабочий снимок, а не дневник всей разработки; длинную завершенную историю переноси в `archive/`.

## Очередь задач

- Основная очередь задач находится в `.aitasks/`: один файл — одна задача. Обрабатывай файлы по имени в алфавитном порядке.
- Порядок обработки задачи:
  1. Прочитать один файл задачи и уяснить результат, который должен получить пользователь.
  2. До реализации продумать решение как опытный инженер: затронутые слои, риски, зависимости, проверки.
  3. Разбить работу на короткий чеклист в `AI_WORK_PLAN.md`.
  4. Выполнить задачу минимальными правками в стиле проекта.
  5. Обновить `AI_CURRENT_CONTEXT.md` коротким итогом и проверками.
  6. Удалить выполненный файл задачи из `.aitasks/` и сделать коммит.
  7. Чеклист выполненных работ скопируй из `AI_WORK_PLAN.md` в `AI_WORK_PLAN_COMPLITED.md`, очисти `AI_WORK_PLAN.md`.
- После решения каждой задачи делай отдельный коммит. Сообщения к коммитам пиши на русском языке и указывай имя AI-ассистента, выполнившего задачу.
- После выполнения всех задач делай пуш.

## Назначение проекта

Проект представляет собой Docker-ориентированный локальный эмулятор для разработки и тестирования Telegram-ботов.

Основной продукт: веб-интерфейс на PHP и HTMX, который минимально имитирует чат Telegram и доставляет похожие на Telegram Bot API updates в контейнеры ботов через webhook или Long Polling.

## Язык проекта

- Ответы пользователю должны быть на русском языке, если пользователь явно не попросил другой язык.
- Сообщения коммитов должны быть на русском языке.
- Техническая документация должна быть на русском языке.
- Markdown-файлы должны быть на русском языке.
- Комментарии в коде должны быть на русском языке.
- Документационные блоки в коде, включая JSDoc, TSDoc, PHPDoc, Python docstring и аналогичные форматы, должны быть на русском языке.
- Имена переменных, функций, классов, API-полей, путей и технических идентификаторов на русский язык не переводить без необходимости.

## Инженерные принципы

- Предпочитать простую и явную реализацию широким абстракциям.
- Держать совместимость с Telegram сфокусированной на реальных задачах разработки.
- Поведение маршрутов, payload, параметров, кодов ошибок и семантики Telegram Bot API должно быть каноничным относительно настоящего Telegram Bot API. Не добавляй неканоничные aliases, compatibility shortcuts, альтернативные URL-формы, дополнительные допустимые параметры или отличающуюся семантику без явного запроса пользователя и отдельного обоснования риска. Если хочется упростить интеграцию с конкретной библиотекой, сначала предложи это пользователю, но не реализуй молча.
- Проект не должен быть привязан к одному bot token: поддержка нескольких ботов и профилей является базовым требованием.
- Поддерживать оба режима получения updates: webhook и Long Polling через `getUpdates`.
- Для неподдерживаемых методов Telegram Bot API возвращать понятные ошибки, а не молчаливые заглушки.
- Сохранять Docker-first workflow.
- Аккуратно относиться к `localhost` в документации и коде: внутри Docker Compose сервисы обычно должны обращаться друг к другу по именам сервисов.
- Хранить постоянные данные разработки в настраиваемой директории.
- Не подключаться к настоящему Telegram, если будущая задача явно не попросит такой режим.

## Ожидаемая архитектура

- Backend HTTP server:
  - API ботов;
  - API профилей;
  - API сообщений;
  - диспетчер webhook;
  - очередь Long Polling updates;
  - локальные маршруты, совместимые с Bot API.
- Frontend:
  - PHP templates и HTMX для интерактивности;
  - Telegram-like интерфейс чата;
  - переключатель и редактор ботов и профилей;
  - инспектор запросов и ответов.
- Хранение:
  - SQLite или другое небольшое локальное файловое хранилище.
- Runtime:
  - Docker и Docker Compose должны оставаться основным способом запуска.

## Стиль кода

- Следовать существующим соглашениям проекта после появления реализации.
- Основной язык проекта: PHP.
- Интерактивность интерфейса строить на HTMX.
- Типы request/response payload должны быть явными.
- Добавлять сфокусированные тесты для генерации update payload, поведения Bot API routes, Long Polling queue и хранения данных.
- Не добавлять production-only инфраструктуру для задач локальной разработки.
- Открывающая фигурная скобка `{` в PHP должна быть в конце строки объявления (стиль K&R / «египетские скобки»), а не на отдельной строке. Исключение: шаблоны (`.php` в `templates/`), где допускается смешение стилей для улучшения читаемости HTML-вставок.

## Безопасность

- Не коммитить секреты, реальные bot token и реальные данные пользователей Telegram.
- Использовать фейковые примеры вроде `123456:local-dev-token`.
- Не удалять пользовательские файлы или настройки IDE без явного запроса.
